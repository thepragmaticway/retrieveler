01 — Setup · Put FFmpeg on PATH
a "well-known path" so you can type ffmpeg from any folder
windows
# Unzip, then move the bin folder to:
C:\ffmpeg\bin\

# Add it to PATH (PowerShell, as admin):
setx /M PATH "$env:PATH;C:\ffmpeg\bin"

# Open a NEW terminal, then verify:
ffmpeg -version
ffprobe -version
macos
# Move binaries to a folder on PATH:
sudo mv ffmpeg ffprobe ffplay /usr/local/bin/

# Gatekeeper may block — allow once:
xattr -d com.apple.quarantine /usr/local/bin/ffmpeg

# Verify:
ffmpeg -version
Goal: typing ffmpeg -version from any directory prints a version. If "command not found" → the PATH entry didn't take, or you didn't open a fresh terminal.

Think of a container like a shipping box 📦 — the box style (MP4 vs MOV) is separate from what's inside it (the codec). You can re-box without re-compressing. More on that in the lab.
04 — Codecs · Encode & Decode
codec = COder + DECoder — squeeze raw pixels small, then rebuild them
The encoder discards what your eyes won't miss (lossy). The decoder reconstructs an approximation. ~150× smaller, near-identical to look at.
05 — Raw Size · Why Compression Exists
raw frame math
# One uncompressed 1080p frame
1920 × 1080 px × 3 bytes  (R,G,B)
  = 6.2 MB  per frame

  + alpha (RGBA) → × 4 = 8.3 MB

# At 24 frames per second:
6.2 MB × 24 × 60 = ~9 GB / min 😱
A 10-min raw 1080p clip ≈ 90 GB. Codecs get it to ~1 GB.
resolution = pixel count = size
04 — Codecs · Newer = Smaller
same 1080p clip, same visual quality — file size by codec generation
The trade-off: H.265/AV1 are much smaller but slower to encode and need newer hardware to decode smoothly. H.264 is still the safe, universal default.
06 — Spatial · Compress Within One Frame
intra-frame · flat areas compress hard · busy detail resists
flat content · cartoon
Huge blocks of identical color → "this whole region is blue." Compresses tiny.
rich content · real movie
Every pixel differs from its neighbor → little to abbreviate. Stays large.
07 — Temporal · I, P & B Frames
inter-frame · don't store every frame — store the CHANGES between them
Only I-frames are whole pictures. P/B-frames store just motion + differences, so they're a fraction of the size.
07 — Temporal · Less Motion, Less Data
P/B frames win big when little changes between frames
steady scene · CCTV, slides
Wall, empty corridor — frames barely change. P-frames near-empty. Small files.
high motion · sports, action
Everything moves every frame — P-frames stay fat. Big files, higher bitrate needed.
08 — Bitrate · Quality vs Bandwidth
bitrate = data per second = the master quality/size dial

09 — FFmpeg · Remux — Change the Box Only
swap container, keep codec → instant, lossless, no re-encoding
# .mov → .mp4 , copy streams as-is
ffmpeg -i big_buck_bunny_1080p_h264.mov \
       -c copy \
       output.mp4
-c copy = stream copy. No decode, no encode. Finishes in seconds, pixel-identical.
09 — FFmpeg · Transcode the Codec
re-encode pixels → H.264 to H.265 → real decode + encode work
CPU — slow, universal
ffmpeg -i input.mp4 \
  -c:v libx265 -crf 28 \
  -c:a copy  out_h265.mp4
GPU — fast, if available
# NVIDIA
-c:v hevc_nvenc
# Apple Silicon
-c:v hevc_videotoolbox
⚠ Transcoding is CPU-heavy. Software H.265 can run at <1× realtime and peg every core. Watch your task manager during the lab.
GPU encoders (NVENC, VideoToolbox, QSV) offload to dedicated silicon — often 5–20× faster, slightly larger files at the same quality. Use them when present.

10 — Pipeline · How a Command Reads
input opts → input → decode → filters → encode → output opts → output
ffmpeg -ss 5 -i in.mp4  -vf scale=1280:-2  -c:v libx264 -b:v 3M  out.mp4
09 — FFmpeg · One Pass, Many Outputs
single input → 3 renditions
ffmpeg -i in.mp4 \
 -vf scale=1920:-2 -b:v 8M out_1080.mp4 \
 -vf scale=1280:-2 -b:v 4M out_720.mp4 \
 -vf scale=640:-2  -b:v 1M out_360.mp4
Decode once, fan out — the classic ABR ladder build.
multi-input · filter graph
# overlay logo onto video
ffmpeg -i video.mp4 -i logo.png \
 -filter_complex \
   "[0:v][1:v]overlay=10:10" \
 out.mp4
11 — Realtime · TCP vs UDP
why live video protocols lean on UDP
TCP — reliable, ordered
UDP — fast, fire-and-forget
For live video a late frame is useless — you want the next frame, not a retransmit of the old one. So RTSP / RTMP favor low-latency UDP transport over waiting for guaranteed delivery.
12 — RTSP · The Camera Is a Server
nearly every IP / CCTV camera exposes an RTSP URL you pull from
No camera on hand? We'll fake one with VLC — serve Big Buck Bunny over RTSP and treat it exactly like a real camera feed.
12 — RTSP · Fake a Camera with VLC
1
VLC → Media ▸ Stream…, add BigBuckBunny_640x360.m4v
2
Click Stream → Next
3
New destination → RTSP → Add
4
Set path /stream, port 8554
5
Turn off transcoding (keep original codec)
6
Stream → it now serves rtsp://127.0.0.1:8554/stream
Tip: enable the "Loop" option so the clip repeats endlessly — behaves like a live camera that never stops.
# Or the one-line CLI equivalent:
cvlc BigBuckBunny_640x360.m4v \
  --loop \
  --sout '#rtp{sdp=rtsp://:8554/stream}'
12 — RTSP · Play, Record, Transcode
treat the RTSP URL just like any other input
play it
ffplay \
 rtsp://127.0.0.1:8554/stream
Live window opens — your "camera" feed.
record · keep codec
ffmpeg -i \
 rtsp://127.0.0.1:8554/stream \
 -c copy -t 30 clip.mp4
No re-encode → cheap. Just saves the stream to disk.
record · transcode
ffmpeg -i \
 rtsp://127.0.0.1:8554/stream \
 -c:v libx265 -b:v 1M \
 -t 30 clip_h265.mkv
Convert live → CPU cost, smaller archive.
This is the heart of a VMS: pull RTSP from cameras → record (copy) or transcode → store / restream. Everything you just learned scales straight into the capstone.

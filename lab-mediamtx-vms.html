The Two-Server Architecture
simulator pretends to be the cameras · VMS pulls, records, serves
MediaMTX calls publishers writers (sources) and players readers. The simulator is a building of writers; the VMS reads them, records them, and re-serves them — exactly the VMS capstone topology.
Setup — Two Instances, Shifted Ports
download mediamtx → two folders → two configs · prepend "1" to simulator ports
cctv-sim/mediamtx.yml

# download: github.com/bluenviron/mediamtx/releases

# run each in its own terminal:
cd cctv-sim  && ./mediamtx     # or mediamtx.exe

Both read the mediamtx.yml sitting next to their executable — that's how two copies coexist on one machine without port collisions.
Simulator — Camera 1: USB Webcam
runOnDemand: ffmpeg starts only when someone watches — like a camera waking up
windows · cctv-sim/mediamtx.yml
paths:
  webcam:
    runOnDemand: >
      ffmpeg -f dshow -i video="USB 2.0 Camera"
      -c:v libx264 -preset veryfast
      -maxrate 4000k -bufsize 8000k
      -pix_fmt yuv420p -g 60
      -f flv rtmp://localhost:11935/$MTX_PATH
    runOnDemandRestart: yes
macos · avfoundation variant
paths:
  webcam:
    runOnDemand: >
      ffmpeg -f avfoundation -framerate 30
      -i "0:none"
      -c:v libx264 -preset veryfast
      -maxrate 4000k -bufsize 8000k
      -pix_fmt yuv420p -g 60
      -f flv rtmp://localhost:11935/$MTX_PATH
    runOnDemandRestart: yes
$MTX_PATH is filled in by MediaMTX (= webcam) — ffmpeg publishes via RTMP back into the same server, which then serves it on every protocol. Find your device name/index with the list commands from the streaming lab (-list_devices true).
Simulator — Camera 2: Your Phone
two ways to wire a phone in: phone PUSHES to the sim, or sim PULLS from the phone
option A · phone publishes (recommended)
Larix Broadcaster — free, no ads, Android + iPhone. In the app: New connection → URL rtsp://<PC-IP>:18554/mobilecam → start broadcasting.
# sim config — nothing to add!
# any publish to an unknown path
# auto-creates it. Just verify:
ffplay rtsp://localhost:18554/mobilecam
option B · sim pulls from phone
Apps that run an RTSP server on the phone (e.g. IP Webcam on Android — free tier is fine). Note the URL the app shows, then:
paths:
  mobilecam:
    source: rtsp://192.168.1.123:8080/cam
    sourceOnDemand: yes
Phone and PC must be on the same Wi-Fi. Find your PC's IP with ipconfig (win) / ifconfig (mac). iPhone has few free RTSP-server apps, which is why push-with-Larix (option A) is the cross-platform recommendation.
Simulator — Cameras 3+4: Virtual Cams from Footage
loop archived CCTV clips forever — cameras that never sleep
paths:
  vcam1:
    runOnInit: >
      ffmpeg -re -stream_loop -1 -i footage1.mp4
      -c:v libx264 -preset veryfast -b:v 2M -pix_fmt yuv420p -g 60 -an
      -f rtsp rtsp://localhost:18554/$MTX_PATH
    runOnInitRestart: yes

  vcam2:
    runOnInit: >
      ffmpeg -re -stream_loop -1 -i footage2.mp4
      -c:v libx264 -preset veryfast -b:v 2M -pix_fmt yuv420p -g 60 -an
      -f rtsp rtsp://localhost:18554/$MTX_PATH
    runOnInitRestart: yes
runOnInit (vs runOnDemand): starts when the server boots and keeps running — a 24/7 camera. -stream_loop -1 loops the file forever; -re paces it at real time.
Footage: any mp4 works — search "CCTV sample footage" on archive.org or pexels.com, or reuse Big Buck Bunny. If the clip is already H.264 you can swap the encode flags for -c copy to save CPU.
Simulator — Verify the Building Is Alive
four cameras, one server — open a player per path
readers — ffplay
ffplay rtsp://localhost:18554/webcam
ffplay rtsp://localhost:18554/mobilecam
ffplay rtsp://localhost:18554/vcam1
ffplay rtsp://localhost:18554/vcam2
same streams, other protocols
# VLC over RTSP
vlc rtsp://localhost:18554/vcam1
# browser · HLS
http://localhost:18888/vcam1
# browser · WebRTC (lowest latency)
http://localhost:18889/vcam1
Checkpoint before continuing: all four paths play. webcam takes a moment to appear (ffmpeg spawns on demand); vcam1/2 are instant; mobilecam needs the phone app broadcasting. One protocol in, every protocol out — that's MediaMTX's core trick.
Lab 1 — VMS Sources via Config File
the VMS becomes a writer-collector: each path pulls one simulator camera
vms/mediamtx.yml
api: yes
apiAddress: :9997

paths:
  cam1:
    source: rtsp://localhost:18554/vcam1
  cam2:
    source: rtsp://localhost:18554/vcam2
  cam3:
    source: rtsp://localhost:18554/webcam
    sourceOnDemand: yes
restart VMS, then read from IT — port 8554
ffplay rtsp://localhost:8554/cam1
ffplay rtsp://localhost:8554/cam2
ffplay rtsp://localhost:8554/cam3
You're now watching simulator cameras through the VMS — sim is the writer, VMS path is the proxy, ffplay is the reader.
sourceOnDemand on cam3: VMS only connects to the webcam when a reader asks — which in turn triggers the sim's runOnDemand ffmpeg. Lazy all the way down.
Lab 2 — VMS Sources via REST API
same result, zero restarts — everything with curl against :9997
# 1 · add a path that pulls vcam1 from the simulator
curl -X POST http://localhost:9997/v3/config/paths/add/cam4 \
  -H "Content-Type: application/json" \
  -d '{"source": "rtsp://localhost:18554/vcam1"}'

# 2 · list configured paths / check live state
curl http://localhost:9997/v3/config/paths/list
curl http://localhost:9997/v3/paths/get/cam4

# 3 · play it (reader) — it's live immediately, no restart
ffplay rtsp://localhost:8554/cam4

# 4 · change the source on the fly, then remove the path
curl -X PATCH http://localhost:9997/v3/config/paths/patch/cam4 \
  -d '{"source": "rtsp://localhost:18554/vcam2"}'
curl -X DELETE http://localhost:9997/v3/config/paths/delete/cam4
Windows quoting: cmd needs the JSON in double quotes with escapes: -d "{\"source\": \"rtsp://...\"}". In PowerShell use curl.exe (plain curl is an alias for Invoke-WebRequest).
Runtime only: API changes live in memory — they're gone after a restart. Persistent cameras belong in the yml; the API is for dynamic add/remove. A real VMS backend stores its camera list in its own DB and re-adds via API on boot.
Lab 3 — Automatic Recording via Config
every frame that reaches a path is segmented to disk
vms/mediamtx.yml — per path
pathDefaults:
  recordPath: ./recordings/%path/%Y-%m-%d_%H-%M-%S-%f
  recordFormat: fmp4
  recordSegmentDuration: 1m
  recordDeleteAfter: 24h

paths:
  cam1:
    source: rtsp://localhost:18554/vcam1
    record: yes
  cam2:
    source: rtsp://localhost:18554/vcam2
    record: no   # live-only path
verify — files appear every minute
# watch segments arrive
ls vms/recordings/cam1/
2026-06-12_10-00-00-000000.mp4
2026-06-12_10-01-00-000000.mp4

# each segment is a normal mp4:
ffplay vms/recordings/cam1/2026-06-12_10-00-00-000000.mp4
recordSegmentDuration chops the archive into bite-size files (1m here for fast lab feedback; 1h is a common production value). recordDeleteAfter is your retention policy — old segments self-delete.
Lab 4 — Recording via API · Auto + Manual
record:true at creation = automatic · patch it live = manual start/stop
# AUTO — new path that records from the moment it exists
curl -X POST http://localhost:9997/v3/config/paths/add/cam5 \
  -d '{"source": "rtsp://localhost:18554/vcam2", "record": true}'

# MANUAL — start recording on an existing path…
curl -X PATCH http://localhost:9997/v3/config/paths/patch/cam2 \
  -d '{"record": true}'

# …let it run a couple of minutes, then stop
curl -X PATCH http://localhost:9997/v3/config/paths/patch/cam2 \
  -d '{"record": false}'

# inspect what's on disk, via API
curl http://localhost:9997/v3/recordings/list
curl http://localhost:9997/v3/recordings/get/cam2
This patch pair — {"record": true} / {"record": false} — is exactly the primitive behind a VMS UI's ⏺ record button: the frontend calls your backend, your backend calls MediaMTX. Manual recording uses the same recordPath/segment settings from Lab 3.
Acceptance Checklist
what "done" looks like for this lab
1
Two MediaMTX instances run side by side — sim on 1xxxx ports, VMS on defaults with API on :9997
2
Simulator serves 4 cameras: /webcam (on demand), /mobilecam (phone), /vcam1 + /vcam2 (looped footage) — all playable in ffplay
3
VMS proxies sim cameras via config-file paths AND via curl-created paths, readable on rtsp://localhost:8554/<path>
4
Auto-recording produces timestamped fmp4 segments under ./recordings/<path>/ with retention configured
5
Manual record start/stop works live via PATCH, and /v3/recordings/list shows the segments
You've now built, by hand, the spine of the VMS capstone: camera fleet → ingest server → live proxy → recorder → API control. The capstone wraps this in your own backend + React frontend.

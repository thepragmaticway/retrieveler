§ 01 — Foundation

OS as a Platform

An Operating System is a platform with two core duties:
  P → R  Allocate and mediate access to system resources (CPU, memory, disk, I/O devices)
  P → P  Provide communication channels between processes (IPC)

Without the OS acting as a controlled intermediary, every program would have to know how to drive its own hardware — and two programs could not safely share a CPU or the same region of memory. The OS abstracts all of that, exposing clean interfaces: system calls.

Many-to-Many Block Diagram

Every process can reach every resource through the OS Resource Manager (P→R), and every process can communicate with every other process through the OS IPC Subsystem (P→P). The OS is always the intermediary — no direct connections exist.

Why Two Separate Concerns?

P→R is about fairness, isolation, and safety. The OS prevents one process from starving another of CPU time, or corrupting another's memory. P→P is about cooperation — letting programs that need to work together exchange data and signals through well-defined channels, not by poking each other's memory directly.

⚙️
CPU

OS time-slices CPU among all running processes via a scheduler. A process never owns the CPU — it borrows it in quanta.

🧠
Memory

Virtual address spaces give each process the illusion of owning all RAM. The MMU + OS translates virtual addresses to physical pages.

💾
Disk / File System

The OS translates file paths to inode or MFT records, managing read/write buffering and permissions for all concurrent accesses.

§ 03 — IPC Types

IPC Mechanisms — Windows & Linux

Both Windows and Linux provide a rich set of IPC primitives. Some exist on both platforms under different names or APIs; a few are platform-exclusive. The right choice depends on whether processes share the same machine, user, or network.

Mechanism Platform How It Works Best For
Anonymous Pipe Both Unidirectional byte stream between a parent and child process. Data flows in one direction through a kernel buffer. Classic use: ls | grep in a shell. Parent–child, sequential data streams
Named Pipe (FIFO) Both Like anonymous pipes but has a filesystem entry (/tmp/mypipe on Linux, \\.\pipe\name on Windows), so unrelated processes can connect to it by name. Two unrelated processes on same machine
Message Queue Both OS-managed queue of discrete messages. Sender writes a message; receiver reads it atomically. Each message has a type/priority. POSIX mq on Linux; MSMQ on Windows. Decoupled producer/consumer, async tasks
Shared Memory Both A region of RAM mapped into the address spaces of two or more processes. Fastest IPC method — no copying. Requires separate synchronisation (mutex/semaphore). shmget/mmap on Linux; CreateFileMapping on Windows. High-throughput, low-latency data sharing
Semaphore / Mutex Both Not a data channel — a synchronisation primitive. A semaphore is a counter; a mutex is a binary lock. Used alongside shared memory or files to prevent race conditions. Coordinating concurrent access to shared state
Unix Domain Socket Linux / macOS Full socket API (stream or datagram) but over a local filesystem path instead of a network address. High performance; supports passing file descriptors between processes. High-performance local IPC (daemons, browsers)
COM / DCOM Windows Component Object Model. Processes expose objects with interfaces; clients call methods via a proxy. DCOM extends this across a network. Foundation for OLE, ActiveX, WinRT. Windows component integration, Office automation
D-Bus Linux A message bus daemon that lets system services and desktop applications send signals and call methods on each other. Heavily used by systemd, GNOME, KDE, PulseAudio. Desktop/system service coordination on Linux
Socket (TCP/UDP) Both Network sockets using the TCP or UDP protocols. Work between processes on the same machine (via loopback 127.0.0.1) or across the internet. The universal IPC for distributed systems. Cross-machine, cross-platform, internet-scale IPC
Signal (kill/sigaction) Linux / POSIX Asynchronous notification sent to a process. Tiny payload (just a signal number, e.g. SIGTERM, SIGINT). The process registers a handler or is killed. Not a data channel — an event notification. Process lifecycle control (start, stop, reload)
Key insight: As you move up the list, IPC mechanisms get faster but more tightly coupled (same machine, same OS). Sockets trade some performance for total flexibility — they work anywhere.

Think of communication protocols as identity and travel documents. Some documents are only accepted locally; others are recognised anywhere in the world.

  • Passport — accepted in 195 countries

TCP in Depth

TCP (Transmission Control Protocol) sits at Layer 4 of the network model. It provides a reliable, ordered, error-checked byte stream between two endpoints (a socket pair: IP address + port). Once a TCP connection is established, it feels like a pipe — you write bytes in one end and they emerge, in order, at the other end, even if the physical path crosses 12 routers and 3 continents.

🔗
Connection-Oriented

A 3-way handshake (SYN → SYN-ACK → ACK) establishes the connection before any data flows. Both sides agree to communicate.

✅
Reliable Delivery

Every segment is acknowledged. Lost packets are retransmitted. The receiving side never sees gaps — the OS reorders fragments before handing data to the application.

🌍
Globally Routable

TCP rides on IP. An IP address identifies any machine on earth. Packets are routed hop-by-hop across the internet's backbone to reach the destination.

§ 05.03 — Pipe Lab

Lab: Experiencing Pipes

A pipe ( | ) connects the stdout of one process directly to the stdin of another — the OS creates a kernel buffer between them. No file is written. The two processes run concurrently; the left process produces, the right process consumes. This is the simplest and oldest form of IPC.

The shell | character is syntactic sugar for the OS creating an anonymous pipe, wiring the write-end to the left process and the read-end to the right process, then spawning both. Data flows left to right as a byte stream.

🪟 Windows — CMD & PowerShell

Lab 5E-W · Pipes on Windows
1
Basic pipe — filter output. dir lists files; findstr filters lines containing the pattern. The two processes communicate via pipe.
CMDanonymous pipe
:: List files, keep only .txt entries
dir /b | findstr ".txt"

:: Count lines in a file
type myfile.txt | find /c ""

:: Chain three processes
dir /b | findstr ".txt" | sort
2
PowerShell object pipe. PowerShell pipes .NET objects, not raw text — each stage receives structured data, not a string.
PowerShellobject pipe
# List processes, filter by name, show selected columns
Get-Process | Where-Object { $_.CPU -gt 1 } | Select-Object Name, CPU, Id

# Count running services
Get-Service | Where-Object Status -eq "Running" | Measure-Object

# Sort files by size, show top 5
Get-ChildItem | Sort-Object Length -Descending | Select-Object -First 5 Name, Length

# Echo text through a pipe chain
echo "hello world" | ForEach-Object { $_.ToUpper() }
3
Named pipe — two separate processes. Open two PowerShell windows. Server writes; client reads. The OS holds the pipe buffer between them.
PowerShell Window A · Named Pipe Servernamed pipe
$pipe = New-Object System.IO.Pipes.NamedPipeServerStream('ipclab', [System.IO.Pipes.PipeDirection]::Out)
Write-Host "Waiting for client..."
$pipe.WaitForConnection()

$writer.AutoFlush = $true
$writer.WriteLine("Hello from the pipe server!")
$pipe.Dispose()
Write-Host "Message sent."
PowerShell Window B · Named Pipe Clientnamed pipe
$pipe = New-Object System.IO.Pipes.NamedPipeClientStream('.', 'ipclab', [System.IO.Pipes.PipeDirection]::In)
$pipe.Connect()
$reader = New-Object System.IO.StreamReader($pipe)
Write-Host ($reader.ReadLine())   # prints: Hello from the pipe server!
$pipe.Dispose()

§ 06 — Messaging

Anatomy of a Message

All communication — whether IPC pipes, network packets, or HTTP requests — is fundamentally just a message sent from one process to another. Every message follows the same intuitive structure you'd recognise from ordinary postal mail.

The Old-Day Mail Analogy

✉️ Physical Letter
Envelope The outer container — carries addressing info without revealing content
To: Recipient name & address — where it must be delivered
From: Sender address — where to send a reply or return
Stamps & marks "Header" data — postmark, priority, postage, handling instructions
Letter inside The actual message — content only the recipient reads
📦 Digital Message
Packet The container — bytes on the wire carrying addressing and data
To: Destination IP + port — the address of the receiving process
From: Source IP + port — so the receiver knows who sent it and can reply
Header Metadata — protocol version, content type, length, auth tokens, timestamps…
Payload The actual data — JSON body, file bytes, HTML, video frames, etc.

The header is everything about the message — it helps routers, proxies, and the receiving application decide what to do with it, without reading the payload. The payload is the application data itself — opaque to the network infrastructure, meaningful only to the endpoint processes.

Generic Message Structure

To
Destination address: IP 203.0.113.42, Port 443 — who receives this message
From
Source address: IP 192.168.1.5, Port 51240 — who sent it; where to reply
Header
Metadata: Content-Type: application/json · Content-Length: 312 · Authorization: Bearer eyJh… · X-Request-ID: f4a9
— describes the message without being the message —
Payload
{ "userId": 42, "action": "createTask", "data": { "title": "Fix login bug", "priority": "high" } }
← the actual application data — what the receiver cares about
§ 07 — HTTP Protocol

HTTP — A Message Protocol on Top of TCP

HTTP (HyperText Transfer Protocol) is a text-based protocol that defines how application-level messages are formatted. It runs most commonly over TCP — but HTTP is not tied to TCP. HTTP/3 runs over QUIC (UDP-based). HTTP could theoretically run over any reliable byte stream.

Think of TCP as the postal road — the infrastructure for moving bytes from A to B. HTTP is the letter format — the convention for what those bytes mean (request / response, method, headers, body).

Your Application (browser, curl, fetch())
talks HTTP
HTTP / HTTP/2 / HTTP/3
message format — method, headers, body
TCP (or QUIC for HTTP/3)
reliable byte stream — connection, ordering, retransmit
IP (Internet Protocol)
addressing & routing across networks
Ethernet / WiFi / Fibre
physical transmission of bits

Workflow

CLIENT
browser / curl
①  TCP SYN → SYN-ACK → ACK   (3-way handshake)
SERVER
nginx / express
②  ─────────────── HTTP Request ──────────────→
GET /users/42 HTTP/1.1 · Host · Accept · Cookie
③  Server processes request, queries DB, builds response
④  ←────────────── HTTP Response ──────────────
200 OK · Content-Type: application/json · Body: {user data}
⑤  TCP connection closed (HTTP/1.0) or kept alive (HTTP/1.1+)

Stateless Nature

HTTP is stateless: each request is completely independent. The server has no built-in memory of previous requests from the same client. After sending a response, the server forgets the exchange entirely.

Imagine calling a bank's customer service line, but the agent cannot see your previous calls. Every time you call, you must re-identify yourself ("account number is…", "last time I asked about…"). HTTP works the same way — each request must carry all necessary context.

GET /profile HTTP/1.1
Cookie: session=abc123
Must send session token every time — server has no memory of previous request
→
200 OK
{ "name": "Alice" }
Server looked up session, responded, then forgot Alice was ever here
POST /orders HTTP/1.1
Cookie: session=abc123
{ "item": "book" }
Next request — totally new. Same session token sent again to re-establish identity
→
201 Created
{ "orderId": 99 }
Server processed, responded, forgot again. State lives in DB and cookie — not in the connection
Statelessness enables scale: any server in a load-balanced pool can handle any request, because no server stores per-connection state. Sessions are tracked via cookies or tokens, not HTTP connections.

Common HTTP Methods

GET

Read a resource. No body. Safe and idempotent — calling it 100 times has the same effect as once.

POST

Create a resource or trigger an action. Carries a body. Not idempotent — each call may create a new record.

PUT / PATCH

Update a resource. PUT replaces it entirely; PATCH modifies specific fields. Both idempotent.

DELETE

Remove a resource. Idempotent — deleting something twice is the same as deleting it once.

OPTIONS

Ask the server what methods and headers it supports. Used by browsers in CORS preflight checks.

HEAD

Like GET but returns headers only — no body. Useful for checking if a resource exists or its size.

Lab 9A — Basic curl requests
GET request — read a resource curl 
# Basic GET
curl https://jsonplaceholder.typicode.com/posts/1

# GET with verbose output — see full request AND response headers
curl -v https://jsonplaceholder.typicode.com/posts/1

# Show only response headers
curl -I https://jsonplaceholder.typicode.com/posts/1

# Pretty-print JSON (pipe to jq)
curl https://jsonplaceholder.typicode.com/posts/1 | jq .
POST request — create a resource curl 
curl -X POST \
     -H "Content-Type: application/json" \
     -d '{"title":"My Post","body":"Hello world","userId":1}' \
     https://jsonplaceholder.typicode.com/posts

# With verbose to see the full round-trip
curl -v -X POST \
     -H "Content-Type: application/json" \
     -d '{"title":"Test"}' \
     https://jsonplaceholder.typicode.com/posts
Send custom headers & inspect timing curl 
# Custom header
curl -H "Authorization: Bearer my-token" \
     -H "Accept: application/json" \
     https://jsonplaceholder.typicode.com/users/1

# Measure timing breakdown
curl -o /dev/null -s -w \
  "DNS: %{time_namelookup}s  TCP: %{time_connect}s  Total: %{time_total}s\n" \
  https://jsonplaceholder.typicode.com/posts/1

Lab 9D — Postman workflow
1
Download and install Postman from postman.com. Create a free account or use without signing in.
2
Create a new Collection called IPC Lab. Add a new request inside it.
3
Set method to GET, URL to https://jsonplaceholder.typicode.com/posts. Click Send. Inspect the response body, headers, and status code.
4
Change method to POST. Open the Body tab → select raw → JSON. Paste {"title":"IPC Lab","body":"test","userId":1}. Send and check the 201 Created response.
5
Open the Console (bottom bar). See the exact HTTP request Postman sent — headers, body, timing. Compare to curl -v output for the same URL.
6
Observe statelessness: Send the GET request 5 times rapidly. Each response is identical — the server has no memory of previous requests. Now add a Cookie: session=fake header and notice the server still responds normally (since typicode ignores cookies) — demonstrating that state must be carried in each request.
Connecting everything: When curl or Postman sends an HTTP request, under the hood it: (1) resolves the hostname via DNS, (2) opens a TCP connection (3-way handshake), (3) writes an HTTP request message over that TCP stream, (4) reads the HTTP response, and (5) closes or reuses the TCP connection. You are now seeing every layer of the stack.
Summary Chain
OS manages P→R and enables P→P  ·  IPC ranges from local pipes to global sockets
TCP = reliable ordered stream that travels worldwide  ·  HTTP = message format on top of TCP
Every message has To · From · Header (metadata) · Payload (data)
HTTP is stateless — each request is self-contained, carries its own context

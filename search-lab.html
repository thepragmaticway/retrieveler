Concept · 01
Linear Search
What is it?

Linear search scans every element from the start until the target is found or the list is exhausted. It requires no sorting and no pre-processing. It is the simplest possible search strategy.

Real World: Finding a Name in an Unsorted Register

Imagine a paper registration list for a conference of 50,000 attendees written in the order people registered — not alphabetically. To find "Zaw Hein Htet" you must read every name from the top until you reach his. On average you read half the list (25,000 names). In the worst case you read all 50,000.

A social network with 1 billion users stored in insertion order would require up to 1 billion comparisons per login — roughly 4 seconds of CPU time per search at 250 million comparisons/second. At 1 million logins per second, that is 4 million CPU-seconds per second. Impossible.

Real World: Virus Scanner

An antivirus scanner checking every byte of a 4 GB drive against a signature list is performing linear search. With no index, it must inspect every byte. This is why full scans take hours — and why indexes and bloom filters are added to accelerate real scanners.

Complexity
CaseComparisonsReal example (n = 1 billion)
BestO(1)Target is the first element
AverageO(n/2)500 million comparisons
WorstO(n)1 billion comparisons — ~4 seconds
When to use it

Linear search is appropriate when the dataset is small (under ~1,000 elements), unsorted and sorting is too expensive, or the search happens only once. For any repeated search over large data, a sorted structure or hash map is always faster.

JScript Implementation Styles

All four examples below implement the same linear-search idea: inspect items one by one until the target is found. The difference is control style. The right choice depends on whether you need index access, early exit, a returned element, or a teaching-friendly implementation.

1. JScript for loop: use this when you need the index, maximum control, or the clearest step-by-step form of the algorithm.

var users = ["Ada", "Linus", "Grace", "Margaret"];
var target = "Grace";
var foundIndex = -1;

for (var i = 0; i < users.length; i++) {
  if (users[i] === target) {
    foundIndex = i;
    break;
  }
}

// foundIndex === 2
  • Concrete example: show that the program checks Ada, then Linus, then Grace, and stops at index 2.
  • Relevant choice: best when you want precise control over iteration count, indexes, and early exit.

2. Array forEach: use this for side effects such as logging or building a trace, not for a clean search API. It does not naturally stop the traversal once a match is found.

var users = ["Ada", "Linus", "Grace", "Margaret"];
var target = "Grace";
var foundIndex = -1;

users.forEach(function (name, index) {
  if (foundIndex !== -1) return;
  if (name === target) {
    foundIndex = index;
  }
});

// foundIndex === 2
  • Concrete example: log every visited element to a debug panel while still detecting the first match.
  • Relevant choice: acceptable for teaching traversal effects, but weaker than for for actual search logic because there is no real break.

3. Array find function: use this when you want the matching element itself and want the code to read like application logic instead of algorithm mechanics.

var users = [
  { id: 101, name: "Ada" },
  { id: 102, name: "Linus" },
  { id: 103, name: "Grace" }
];

var match = users.find(function (user) {
  return user.id === 103;
});

// match === { id: 103, name: "Grace" }
  • Concrete example: find the first user record whose id matches the current login request.
  • Relevant choice: best for production-style code when readability matters more than exposing the low-level loop.

4. Custom find implementation: use this when teaching how built-ins work internally or when you want one reusable helper with your own matching rule.

function findInArray(items, predicate) {
  for (var i = 0; i < items.length; i++) {
    if (predicate(items[i], i, items)) {
      return items[i];
    }
  }
  return undefined;
}

var users = [
  { id: 101, name: "Ada" },
  { id: 102, name: "Linus" },
  { id: 103, name: "Grace" }
];

var match = findInArray(users, function (user) {
  return user.name === "Grace";
});
  • Concrete example: teach that the built-in find is still just a linear scan wrapped behind a helper.
  • Relevant choice: best when abstraction is part of the lesson, or when you need custom behavior across multiple searches.

Short rule: choose for for control, forEach for side-effect traversal, built-in find for clean application code, and custom find when you want to teach or encapsulate the algorithm.

Concept · 02
Binary Search
What is it?

Binary search works on a sorted dataset. At each step it picks the middle element. If the target is smaller, it discards the right half. If larger, it discards the left half. Each comparison eliminates half the remaining candidates.

Real World: Dictionary Lookup

Nobody starts at page 1 of a dictionary to find "zebra." You open near the end, see "M," realise the target is to the right, open further right, see "U," narrow again. You find a 300,000-word dictionary in about 18 page-opens — log₂(300,000) ≈ 18.

Real World: Git bisect

Git's bisect command finds which commit introduced a bug using binary search over commit history. With 1 million commits, it finds the culprit in at most 20 tests — not 1 million. Every developer uses this without necessarily knowing the name of the algorithm.

Complexity
CaseComparisonsReal example (n = 1 billion)
BestO(1)Target is the midpoint
AverageO(log n)~30 comparisons
WorstO(log n)30 comparisons — microseconds
The cost: sorting

Binary search requires a sorted array. Sorting n elements costs O(n log n). This upfront cost is paid once; every subsequent search costs only O(log n). For any dataset searched more than once, the trade-off is always worth it.

JScript Implementation Styles

Binary search has fewer useful iteration styles than linear search because the algorithm depends on direct index access and repeated midpoint calculation. In practice, the plain while loop is the relevant form, and helper functions are usually just wrappers around that same loop.

1. Index-controlled while loop: this is the standard binary-search implementation because you must update left, right, and mid explicitly on every step.

var numbers = [3, 8, 12, 21, 34, 55, 89];
var target = 34;
var left = 0;
var right = numbers.length - 1;
var foundIndex = -1;

while (left <= right) {
  var mid = Math.floor((left + right) / 2);

  if (numbers[mid] === target) {
    foundIndex = mid;
    break;
  }

  if (numbers[mid] < target) {
    left = mid + 1;
  } else {
    right = mid - 1;
  }
}

// foundIndex === 4
  • Concrete example: searching for 34 checks 21, then 55, then lands on 34.
  • Relevant choice: best when you want to teach exactly how the search interval shrinks.

2. Recursive implementation: this expresses the same logic in a more mathematical form, with each call representing the remaining half of the array.

function binarySearch(items, target, left, right) {
  if (left > right) return -1;

  var mid = Math.floor((left + right) / 2);

  if (items[mid] === target) return mid;
  if (items[mid] < target) return binarySearch(items, target, mid + 1, right);
  return binarySearch(items, target, left, mid - 1);
}

var numbers = [3, 8, 12, 21, 34, 55, 89];
var foundIndex = binarySearch(numbers, 34, 0, numbers.length - 1);
  • Concrete example: each recursive call discards half the current range until only the matching slot remains.
  • Relevant choice: useful for explanation, but the iterative loop is usually clearer for production debugging.

3. Wrapper function for repeated lookups: application code often hides the control loop behind a reusable helper so callers can start with an unsorted user list, derive a sorted ID index once, and then reuse it for many searches.

function findSortedUserId(sortedIds, targetId) {
  var left = 0;
  var right = sortedIds.length - 1;

  while (left <= right) {
    var mid = Math.floor((left + right) / 2);
    if (sortedIds[mid] === targetId) return mid;
    if (sortedIds[mid] < targetId) left = mid + 1;
    else right = mid - 1;
  }

  return -1;
}

var users = [
  { id: 140, name: "Grace" },
  { id: 101, name: "Ada" },
  { id: 170, name: "Linus" },
  { id: 125, name: "Margaret" }
];

var sortedIds = users
  .map(function (user) { return user.id; })
  .sort(function (a, b) { return a - b; });

var index = findSortedUserId(sortedIds, 125);
// sortedIds === [101, 125, 140, 170]
// index === 1
  • Concrete example: derive a sorted ID list from an unsorted user directory once, then reuse it for repeated lookups by ID.
  • Relevant choice: best when the original data is unsorted but you can afford one preprocessing step to make future searches fast.

Short rule: binary search is mainly about interval control, so direct indexed loops and small wrappers are the practical JScript forms. Methods like forEach or find are the wrong fit because they scan linearly and throw away the algorithm's advantage.

Concept · 03
Hash Search
What is it?

Hash search converts the key directly to an array index using a hash function. Rather than scanning (linear) or narrowing (binary), it jumps to the exact slot in one step. Average case is O(1) — constant time regardless of dataset size.

Real World: Database Index

When you run SELECT * FROM users WHERE username = 'alice', a hash index on the username column converts 'alice' to a slot number and retrieves the row directly — no row-by-row scan. PostgreSQL, MySQL, and Redis all use hash indexes for exact-match lookups.

Real World: DNS Resolution

Your browser converts "google.com" to an IP address using a local DNS cache — a hash map of domain → IP. The lookup is instant regardless of how many domains are cached, because the domain name is hashed directly to a cache slot.

The three steps

Step 1 — Hash the key: convert the key string to a number by summing or combining char codes.

Step 2 — Division method: slot = hash(key) mod slotCount — clamp the hash to a valid array index.

Step 3 — Check the slot: if the slot contains the key, return the value. If empty, the key does not exist. If occupied by a different key, a collision occurred — probe the next slot.

Complexity
CaseStepsNote
Best / AverageO(1)Direct slot hit, no collision
CollisionO(k)k = chain length at that slot
Worst (all collide)O(n)Degrades to linear — rare with good hash
JScript Implementation Styles

Hash search is less about iteration across the full dataset and more about direct addressing. The implementation style depends on whether you use a built-in object map, a built-in Map, or a teaching-oriented custom hash table.

1. Plain object lookup: the simplest JScript-style hash search is to store values by key on an object and retrieve them directly.

var userByName = {
  ada: { id: 101, role: "admin" },
  grace: { id: 102, role: "editor" },
  linus: { id: 103, role: "viewer" }
};

var match = userByName["grace"];

// match === { id: 102, role: "editor" }
  • Concrete example: look up the grace user record without scanning every user.
  • Relevant choice: best when keys are simple strings and you want the clearest demonstration of constant-time lookup.

2. Map lookup: use Map when keys are not limited to plain object property rules or when you want an explicit hash-map API.

var sessions = new Map();
sessions.set("token-101", { userId: 101, active: true });
sessions.set("token-102", { userId: 102, active: true });

var session = sessions.get("token-102");

// session === { userId: 102, active: true }
  • Concrete example: retrieve the session attached to an API token in one lookup.
  • Relevant choice: better than a plain object when the codebase wants explicit insertion, lookup, and membership operations.

3. Custom hash table implementation: use this when teaching how the slot computation and collision handling actually work internally.

function hash(key, size) {
  var total = 0;
  for (var i = 0; i < key.length; i++) {
    total += key.charCodeAt(i);
  }
  return total % size;
}

function getFromTable(table, key) {
  var slot = hash(key, table.length);
  var bucket = table[slot] || [];

  for (var i = 0; i < bucket.length; i++) {
    if (bucket[i].key === key) {
      return bucket[i].value;
    }
  }

  return undefined;
}

var table = [];
table[3] = [{ key: "grace", value: { id: 102, role: "editor" } }];

var match = getFromTable(table, "grace");
  • Concrete example: compute the slot for grace, inspect that bucket, then scan only the collided entries inside it.
  • Relevant choice: best for explaining why average-case lookup is constant time but collision handling can introduce a tiny local linear scan.

Short rule: use plain objects or Map for real application lookup, and use a custom table only when you need to explain the mechanics behind hashing and collisions.

Search Summary
What this compares

This panel compares the three search strategies against the same dataset size n. Linear search grows directly with the number of records, binary search grows with the number of halvings needed, and hash lookup stays nearly flat for exact-match average-case retrieval.

How to read the graph

The y-axis shows concrete operation counts for the selected dataset size. Each bar also shows the matching Big O label, so you can connect the abstract complexity class to a real number of comparisons or slot checks.

For this summary view, the comparison uses representative costs: linear worst-case n, binary worst-case ceil(log2(n)), and hash average-case 1. Hash collision worst-cases still exist, but they are intentionally excluded here because they are not the normal operating case of a healthy hash table.

What changes as n grows

Moving from 1,024 records to 1 trillion records barely changes binary search and almost does nothing to hash lookup, but it makes linear search explode. That contrast is the main reason production systems sort data, build indexes, or use hash maps instead of scanning raw lists repeatedly.

Concept · 05
Log₂ Appendix
The core meaning

log₂(x) means: "what exponent do I put on 2 to get x?" If 2^7 = 128, then log₂(128) = 7. The log value is not a separate mysterious number. It is just the exponent.

What to memorize

You do not need an infinite table in your head. For binary search and computer-size intuition, memorize the ladder from 0 to 9, then the decade anchors 10, 20, 30, and 40.

Why +10 in log means ×1024 in x

The jump is always the same because 2^(n+10) = 2^n × 2^10. And 2^10 = 1,024. So every time the log value increases by 10, the actual data size increases by 1,024 times.

Example 1: from log₂(x) = 10 to 20 means going from 1,024 to 1,048,576.
Example 2: from 20 to 30 means multiplying again by 1,024.
Example 3: from 30 to 40 means multiplying again by 1,024.
Practice · 05
Recognition pattern

Read log and exponent in both directions until they feel identical:

If log₂(x) = 8, then x = 256.
If x = 512, then log₂(x) = 9.
If log₂(x) = 20, then x ≈ 1M.
If x ≈ 1B, then log₂(x) ≈ 30.
Fast drills
Drill 1: log₂(x) = 6 → 64
Drill 2: x = 128 → 7
Drill 3: log₂(x) goes from 10 to 20 → x multiplies by 1,024
Drill 4: log₂(x) goes from 20 to 40 → x multiplies by 1,024 × 1,024 = 1,048,576
Binary search intuition

This is why binary search stays small even when data gets huge. If the dataset is around 1K, worst-case steps are about 10. At 1M, they are about 20. At 1B, about 30. At 1T, about 40.

The data size explodes by factors of 1,024, but the number of binary-search decisions only rises by 10 each decade. That is the entire power of O(log n) in one mental picture.

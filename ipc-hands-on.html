§ 01 — IPC: Anonymous Pipe

IPC: Anonymous Pipe

The shell | character asks the OS for an anonymous pipe: a kernel buffer with a write-end wired to the left process's stdout and a read-end wired to the right process's stdin. Both processes run concurrently. No file is written. This is the simplest, oldest, and most-used form of IPC.

The labs below combine standard shell tools (echo, ls/dir, findstr/grep, nc/ncat) with regxer.js, a tiny Node.js CLI that runs a JavaScript regex against text from a file or from stdin — making it a natural pipe consumer.

regxer.js arguments

FlagMeaning
-f <name>Regex function: search, match, or test
-r "<pattern>"Regex pattern (quote it so the shell doesn't expand it)
-gEnable global matching (match returns all matches)
-i <file>Read input from a file
-o <file>Write output to a file

If -i is omitted, regxer.js reads from stdin when something is piped to it. If -o is omitted, output is printed as JSON on stdout — which means another pipe stage can consume it.

§ 01.01 — Hands-On

Pipe hands-on with regxer.js

Lab 1A — ls / dir | regxer.js
1
List the files in the ipc/ folder and pipe the listing into regxer.js. The regex function match with the global flag returns every match found in stdin.
bash / macOS / Linuxls | regxer.js
# Find every ".js" file name fragment in the directory listing
ls | node regxer.js -f match -g -r "\\w+\\.js"
Windows · cmd / PowerShelldir | regxer.js
:: List file names only, then keep entries ending in .js
dir /b | node regxer.js -f match -g -r "\w+\.js"
What just happened: the shell created a kernel pipe, started ls / dir as Process A, started node regxer.js … as Process B with its stdin.isTTY set to false. regxer.js detected piped input and read the directory listing as a string, then ran String.prototype.match against it. The JSON result is printed on stdout.
Lab 1B — echo "test123" | regxer.js
1
The simplest possible producer. echo writes its argument to stdout, and regxer.js reads it from stdin. echo does not read stdin — always give it text after the command.
echo with an argumentecho | regxer.js
# Does the input contain three or more digits?
echo "test123" | node regxer.js -f test -r "\\d{3,}"

# Extract the matched digits
echo "test123" | node regxer.js -f match -r "\\d+"

# Where does the digit run start? search returns an index
echo "test123" | node regxer.js -f search -r "\\d+"
2
Compare the three function modes: test returns a boolean, match returns the matched text(s), search returns a zero-based index.
Lab 1C — myecho as producer (argument or stdin) | regxer.js
1
myecho covers the case echo can't: with an argument it behaves like echo; with no argument it reads from stdin. That makes it usable both at the start of a pipe (as a producer) and in the middle (as a passthrough that reads upstream stdin).
myecho — argument mode (producer)myecho arg | regxer.js
# Argument mode: myecho prints its argument, regxer consumes it
java myecho "test123" | node regxer.js -f match -r "\\d+"

# Same shape as echo, but the producer is myecho
java myecho "hello-2026" | node regxer.js -f test -r "\\d{4}"
2
With no argument, myecho reads stdin — so you can place it in the middle of a chain. Compare this with echo in Lab 1B, where echo could only sit at the start.
myecho — stdin mode (passthrough)echo | myecho | regxer.js
# echo produces text → myecho reads it from stdin → regxer consumes it
echo "test123" | java myecho | node regxer.js -f match -r "\\d+"

# myecho as the consumer at the end of a pipe — argument is ignored when stdin has data?
# No — myecho prefers argument when one is given; remove it to read stdin:
echo "abc 42 xyz" | java myecho
3
Interactive mode — myecho with no argument and no upstream pipe. Run java myecho at the head of the pipeline. It will sit and wait for stdin — type your text from the keyboard, press Enter, then send EOF to signal "input finished" so myecho can forward the bytes to the next stage.
myecho — keyboard inputjava myecho | regxer.js
# No argument → myecho reads from your terminal (the keyboard is stdin)
java myecho | node regxer.js -f match -r "\\d+"

# Now type at the prompt:
test123
# Press Enter, then send EOF:
#   Linux / macOS : Ctrl+D
#   Windows       : Ctrl+Z then Enter
# regxer prints the JSON match.
Reminder: with no argument and no upstream pipe, java myecho blocks on the keyboard. Type your line and press Enter, then close stdin with Ctrl+D (Linux/macOS) or Ctrl+Z + Enter (Windows). Until you send EOF, downstream stages won't see anything — the pipe is still waiting for the producer.
Why this matters: regxer.js checks process.stdin.isTTY. When you pipe to it, that flag is false, so it reads the byte stream. When you run it directly with no -i and no pipe, it refuses and prints a helpful error. myecho uses the same trick — argument vs stdin — so you can see two different programs agreeing on the same kernel convention.
§ 02 — IPC: Socket

IPC: Socket — socketer.js

Before we dive in, here's the layered stack the rest of this page climbs through. Each layer is built on top of the one below — same bytes, more abstraction at each step. The labs below correspond one-to-one with the layers in this diagram.

↑ higher abstraction · your application
HTTP Application express-server.js
(routing & middleware)
HTTP Library http-server.js
(Node http module)
HTTP over Raw Socket http-socketer.js
(hand-parsed HTTP/1.1)
Socket (TCP) socketer.js · nc / ncat
(raw byte stream)
IPC (OS Kernel) pipes · sockets · kernel buffers
(system calls)
↓ lower abstraction · OS / wire
Where pipes connect two processes on the same machine through the OS kernel, sockets connect two processes through the OS network stack — same machine or different machines, doesn't matter. socketer.js is a minimal TCP client / server written in Node, modelled on nc / ncat.

socketer.js arguments

FlagMeaning
-l <port>Listen as a TCP server on the given port
[host]Optional bind host in server mode (e.g. 127.0.0.1)
-b, --brokerBroadcast every client's data to every other connected client (group chat)
<host> <port>Run as a TCP client, connect to that server
-h, --helpShow help

Server mode writes incoming client bytes to its own stdout, and forwards anything typed into its stdin to all connected clients. Client mode does the opposite: it pipes its stdin to the socket and writes the socket's response on stdout. When the client's stdin closes (e.g. a pipe finishes), the client closes its write side.

One-to-many broadcast (group chat)

Lab 2D — Broker mode
1
The -b / --broker flag turns the server into a fan-out hub: every byte a client sends is forwarded to every other connected client. Combined with the server's own stdin (also broadcast), this gives you a tiny group chat.
T1 brokersocketer.js -l -b

Open two more terminals and connect both as clients.
two clientsT2 + T3

Type a line in Terminal 2. Terminal 3 sees it (broker forwarded it). Type in Terminal 3 — Terminal 2 sees it. Type into the broker server itself (Terminal 1) — both clients see it. You've built a chat hub in fewer than 250 lines of code.
Try it: add a fourth client, then disconnect one with Ctrl+C. The remaining clients stay connected. socketer.js tracks the set of live sockets and drops the closed ones — read startServer in socketer.js to see the Set<Socket> in action.
§ 02.03 — Pipe ↔ Socket

Pipe hands-on with socketer.js

Pipes and sockets compose. A client's stdin is a pipe; a client's socket is the network. socketer.js wires them together so anything piped into a client travels straight across TCP into the server's stdout. Combine that with regxer.js and you have a tiny stream-processing pipeline that spans machines.
Lab 2E — ls / dir | socketer (client)
1
Make sure a socketer server is already running (Lab 2A). Then in another terminal, pipe a directory listing through a client. The listing flows: ls stdout → kernel pipe → client stdin → TCP socket → server stdout.
bash · client receives stdinls | socketer
ls | node socketer.js 127.0.0.1 9000
Windows · cmddir | socketer
dir /b | node socketer.js 127.0.0.1 9000
Lab 2F — echo / myecho "Hello" | socketer
1
The shell echo writes its argument to stdout — socketer.js client forwards that stdout across TCP. Remember: echo needs an argument; it never reads stdin.
echo with an argumentecho | socketer
echo "Hello" | node socketer.js 127.0.0.1 9000
# server terminal prints: Hello
2
myecho works the same way in argument mode, and also lets you read from stdin when no argument is given — handy if you want a passthrough stage before the socket.
myecho variantsmyecho | socketer
# Argument mode
java myecho "Hello" | node socketer.js 127.0.0.1 9000

# Stdin mode — myecho sits between echo and the socket
echo "Hello" | java myecho | node socketer.js 127.0.0.1 9000
3
Interactive mode — myecho with no argument. Use java myecho at the head of the pipe to send a line you type from the keyboard across the TCP socket to the server in Lab 2A.
myecho — keyboard input → socketjava myecho | socketer
# No argument → myecho reads from your keyboard, the socket carries it
java myecho | node socketer.js 127.0.0.1 9000

# Type at the prompt, then send EOF:
Hello from the keyboard
# Press Enter, then:
#   Linux / macOS : Ctrl+D
#   Windows       : Ctrl+Z then Enter
# server terminal prints the line you just typed.
Reminder: java myecho with no argument blocks on the keyboard until you press Enter and send EOF (Ctrl+D on Linux/macOS, Ctrl+Z + Enter on Windows). Only then does myecho finish, which closes the pipe to socketer's stdin, which in turn calls socket.end() on the TCP connection.
Behavior detail: when stdin ends (the echo / myecho process finishes), wireProcessInput in socketer.js calls socket.end() in client mode — the client cleanly closes its write side and exits. The server stays up for the next connection.
Lab 2G — Chain regxer + socketer
1
Now compose the CLIs into a single pipeline. echo (or myecho) produces text, regxer.js extracts a JSON match, the JSON travels across TCP into the server.
three-stage pipeline · echo producerecho | regxer | socketer

# ...and in stdin mode (four stages — myecho as passthrough)

2
You can replace the last stage with nc or ncat against the same server — they speak raw TCP too, so any TCP listener works.
interop with ncat / ncecho | regxer | nc
# With ncat (nmap project) or nc (BSD/GNU)
echo "test123" | node regxer.js -f match -r "\\d+" | ncat 127.0.0.1 9000

# myecho works the same way
java myecho "test123" | node regxer.js -f match -r "\\d+" | ncat 127.0.0.1 9000

# Also works in reverse: ncat server, socketer client
ncat -l 9000                       # in terminal 1
echo "hi" | node socketer.js 127.0.0.1 9000
Why interop works: at the wire level, TCP is just bytes. None of these tools impose a protocol; they ship the bytes you give them. Pipes glue them together at the process layer.
§ 03 — http-socketer.js

HTTP over a raw TCP socket

http-socketer.js takes the same raw net.createServer from socketer.js and adds just enough byte-level parsing to speak HTTP/1.1 — a request line, CRLF-terminated headers, a blank line, and a body. It serves files from the current working directory.

Arguments

FlagMeaning
-l <port>Listen mode, raw HTTP-over-TCP server
[host]Optional bind host
-h, --helpShow help

Behavior

Only GET is supported. Targets must start with /. Files are resolved relative to the current working directory when you start the process. Missing files return 404 Not Found; non-GET methods return 405. Common text types (.html, .js, .json, .css, .txt) are served with inline-friendly content types.

§ 04 — http-server.js

HTTP using Node's http module

http-server.js does the same job as http-socketer.js with far less code — it uses Node's built-in http module, which handles the request line, header parsing, and response framing for you. Same behavior, half the surface area.

Arguments

FlagMeaning
-l <port>Listen mode on the given port
[host]Optional bind host
-h, --helpShow help

Behavior

Only GET; missing files return 404; non-GET returns 405 Method Not Allowed with an Allow: GET header; files resolved against process.cwd(). Compare to http-socketer.js — same contract, different layer.

§ 05 — ipc-express / express-server.js

Express — a framework on top of http

Express is a thin web-framework layer on top of Node's http module. It adds routing, middleware ordering, and ergonomics for sending JSON, serving static files, and producing typed responses. Same TCP stack underneath — same bytes on the wire.
Reference: see ipc-express/README.md for the full description, and ipc-express/express-server.js for the source. The labs below mirror those instructions.

Lab 5C — Observe middleware order
1
Express resolves middleware top-to-bottom. In express-server.js the order is: (1) GET /api/hello, (2) express.static(...), (3) catch-all GET * → 404, (4) final middleware → 405 Method Not Allowed.
verify each branchcurl
# 1. specific API route matches first
curl -i http://127.0.0.1:9000/api/hello

# 2. static file falls through to express.static
curl -i http://127.0.0.1:9000/index.html

# 3. unknown GET path falls through to the catch-all 404
curl -i http://127.0.0.1:9000/does-not-exist

# 4. non-GET method falls through to the 405 middleware
curl -i -X POST http://127.0.0.1:9000/api/hello
The rule, in one line: register specific routes first, generic handlers last. Reverse the order and a wildcard /api/* will swallow the more specific /api/hello.

01 — A Video File Is Header + Frames
mp4 · webm · mkv — all share this shape
HEADERfile type · brand
INDEX / METADATAtracks · codecs · timing · sample map
MEDIA DATA — interleaved framesV A V A V A V A …
The header says what the file is. The index (mp4: moov) is a map: which byte is which frame, at what timestamp. The data (mp4: mdat) is the actual interleaved A/V bytes.
01 — Same Idea, Different Names
the index and data are always there — the boxes are just renamed
ContainerHeader boxIndex / metadataMedia data
MP4 / MOVftypmoov (atoms/boxes)mdat
WebM / MKVEBML headerSegment ▸ Tracks + CuesClusters
MPEG-TS— (no global header)PAT / PMT (recurring)188-byte packets
MPEG-TS is the outlier: instead of one header up front, it sprinkles small index packets (PAT/PMT) throughout the stream — so a player can tune in at any point. That's exactly what live broadcast needs. More in Part 3.
01 — Why Interleave A & V?
so the player reads sound + picture for the same moment, in one forward pass
interleaved · good
A & V for each instant sit next to each other → sequential read, small buffer. Perfect for streaming off disk or network.
all-V-then-all-A · bad
Player would have to jump across the whole file to pair audio with video. Huge buffering, impossible to stream.
02 — Progressive Download
start playing the front while the rest still downloads
The player grabs the header + index first, learns where frames live, then decodes the chunks it already has while the network keeps filling the buffer ahead. No need to wait for the full file.
02 — The Catch: Where Is the Index?
progressive playback needs the index BEFORE the data
index at TAIL — default mp4
ftyp
mdat (data)
moov
Player can't find frames until it reaches the end → must download (almost) the whole file before playback can begin. ✗ slow start
index at FRONT — faststart
ftyp
moov
mdat (data)
Index arrives in the first few KB → player starts decoding almost immediately. ✓ instant start
Encoders write moov last by default (final sizes are only known when encoding ends). For the web you must move it to the front.
02 — Lab · Move the Header, Watch It Play
# 1 · Index at TAIL (default) — the "slow" file
ffmpeg -i big_buck_bunny_1080p_h264.mov \
       -c copy tail.mp4

# 2 · Index at FRONT — faststart, web-ready
ffmpeg -i big_buck_bunny_1080p_h264.mov \
       -c copy -movflags +faststart front.mp4

# 3 · Inspect atom order
ffprobe -v trace tail.mp4  2>&1 | grep -E "moov|mdat"
ffprobe -v trace front.mp4 2>&1 | grep -E "moov|mdat"
<!-- 4 · Play both in a browser -->
<video src="tail.mp4" controls></video>
<video src="front.mp4" controls></video>
Expected: front.mp4 starts almost instantly; tail.mp4 hangs on a black frame / spinner until much more has buffered.
Sharpen it: serve over a throttled connection (DevTools ▸ Network ▸ Slow 3G) to make the difference dramatic.
Note: if the server supports HTTP range requests, a browser can fetch the tail moov with an extra round-trip and still play — just with a visible delay. Faststart removes that round-trip entirely.
03 — Inside the Video: NAL Units
H.264 / H.265 isn't one blob — it's a sequence of self-describing packets
NAL = Network Abstraction Layer. The codec emits these chunks so they can be packed into a file or dropped into network packets unchanged — same units, two destinations.
03 — And the Audio: Frames
AAC encodes audio into fixed little frames, each independently decodable
Like P-frames for video, each audio frame is small and regular — easy to packetize, easy to drop one without wrecking the rest.
03 — One Source, Two Destinations
the same NAL + audio packets go into a file OR onto the wire
A file is just packets at rest; a stream is the same packets in motion. The protocol decides how they're framed, addressed, and paced.
03 — Streaming Protocols — Same Packets, Different Wire
ProtocolTransportLatencyWhere it's used
RTSP + RTPUDP (mostly)~0.2–0.5 sCCTV / IP cameras — pull a live feed
RTMPTCP~2–5 sIngest to streaming servers (legacy, still common)
WebRTCUDP (SRTP)< 0.5 sBrowser calls, real-time interactive, VMS live grid
UDP / MPEG-TSUDP~0.5–1 sIPTV, broadcast contribution, multicast
HTTP (HLS/DASH)TCP~3–30 sScale to millions via CDN — VOD & live archive
Pattern: UDP = low latency, may drop (live, interactive). TCP/HTTP = reliable, higher latency, scales on CDNs (broadcast to the masses). Pick by how "live" it must feel vs how many viewers.
03 — Try It · Send File over UDP/TS
start simple: one sender → one player, then fan out
1 · sender — single output
ffmpeg -re -i big_buck_bunny_1080p_h264.mov \
  -c copy -f mpegts \
  udp://127.0.0.1:1234?pkt_size=1316
2 · play it with ffplay
ffplay udp://127.0.0.1:1234
-re paces at real-time. -c copy works — file is already H.264/AAC.
Now fan out — plain UDP hits one address, so duplicate the output with tee, one port per player:
ffmpeg -re -i big_buck_bunny_1080p_h264.mov -c copy -f tee \
  "[f=mpegts]udp://127.0.0.1:1234|[f=mpegts]udp://127.0.0.1:1235"

ffplay udp://127.0.0.1:1234          # player A
ffplay udp://127.0.0.1:1235          # player B
vlc    udp://@:1235                 # player B alt  (@ = listen on this port)
03 — Multicast · One Send, Many Receivers
stop duplicating at the sender — let the network copy for you
unicast · sender copies N times
3 players = 3× the upload bandwidth from one box.
multicast · sender sends once
One stream out; the network duplicates only to those who joined the group.
sender → group address
ffmpeg -re -i bbb.mov -c copy -f mpegts \
  "udp://239.0.0.1:1234?pkt_size=1316&ttl=1"
receivers join the group
ffplay udp://239.0.0.1:1234
vlc    udp://@239.0.0.1:1234  # @group
239.0.0.0/8 = the local/private multicast range (safe for a LAN). ttl=1 keeps packets on your subnet. Receivers "join" via IGMP automatically when they open the URL. ⚠ Most Wi-Fi handles multicast poorly — demo on wired LAN, or fall back to the unicast/tee approach.
03 — Try It · Webcam / Screen → Stream
raw capture must be ENCODED first — no -c copy
windows · dshow + gdigrab
# list devices
ffmpeg -list_devices true -f dshow -i dummy

# WEBCAM in:
-f dshow -i video="Integrated Camera"
# SCREEN in (swap the input):
-f gdigrab -framerate 30 -i desktop
macos · avfoundation
# list devices (note the indexes)
ffmpeg -f avfoundation -list_devices true -i ""

# WEBCAM in (video:audio):
-f avfoundation -framerate 30 -i "0:0"
# SCREEN in (use "Capture screen" index):
-f avfoundation -framerate 30 -i "1"
encode + send — identical after the input
# append this to whichever input above:
  -c:v libx264 -preset ultrafast -tune zerolatency -b:v 2M -g 30 -pix_fmt yuv420p \
  -f mpegts udp://239.0.0.1:1234?pkt_size=1316
watch the live capture
# low-latency playback
ffplay -fflags nobuffer \
  udp://239.0.0.1:1234
-fflags nobuffer trims the player's buffer so the preview stays close to live.
-g 30 = a keyframe every second, so players joining mid-stream sync within ~1s. Lines shown wrapped — type as one line, or use your shell's continuation: \ bash/zsh · ^ cmd · ` PowerShell.
The Whole Journey

HTTP Capstone — Request & Reply

A small capstone that wraps the IPC series: learn why most applications speak HTTP, the exact shape of a request and reply, and how the browser can send those requests two different ways — plain HTML forms and AJAX fetch — using the express-auth sample app.

§ 00 — Setup

Run the capstone app

Every lab below uses the express-auth sample under express-auth/. It's an intentionally small Express app: one server file, one in-memory store, a few static HTML pages, and a handful of routes that cover all four CRUD verbs against a single user account resource.
Lab 0 — Install & start
1
From the repo root, switch into express-auth/ and install once. The only dependency is express.
installnpm install

2
Start the server on port 3000 and leave it running. The process prints its bind address on stderr.
startexpress-server.js -l

3
Open http://127.0.0.1:3000/ in a browser. You'll be redirected to /login because there's no session cookie yet — that redirect is your first HTTP reply, and the rest of this page explains exactly what's flying back and forth.
Why an auth app? Signup, login, change-password, and deactivate cover the four operations every CRUD app does: create, read, update, delete. Authentication just happens to be the most relatable example of the user resource.
§ 01 — Concept

Why most applications speak HTTP

HTTP is a request/reply protocol over a TCP socket — the same socket layer you saw in the IPC Hands-On lab. A client sends one request; the server returns one response; the conversation is finished. That tiny contract turned out to be enough to build almost every application you use:

  • Universal client — every OS ships a browser, and every browser speaks HTTP. No client install needed.
  • Stateless — each request is self-contained, so servers scale horizontally and load-balancers don't have to track conversations.
  • Text on the wire — you can read raw HTTP with your eyes (you did exactly that with socketer.js) and inspect it with browser DevTools.
  • Verb-based — four common methods cover almost every operation on a resource: read, create, update, delete.
  • Layered — HTML, JSON, file downloads, AJAX, streaming — all the same envelope, different payloads.

The recipe for writing most applications is the same every time:

  1. Pick the resources the app manages (users, posts, orders, …).
  2. Decide which URL each resource lives at (/users, /posts/42).
  3. For each operation, pick the matching method — GET to read, POST to create, PUT to update, DELETE to remove.
  4. Choose how the browser sends the request — HTML form for whole-page flows, AJAX when the page controls its own flow.
  5. Handle the reply — a new page (server-driven flow) or a JSON object (page-driven flow).
From IPC to HTTP: in the previous lab you watched bytes flow through a kernel pipe, then through a TCP socket, then as a hand-typed HTTP request, then through Node's http module, then through Express. This page sits at the very top of that stack — same bytes, now structured into a contract you can build a whole product on.
§ 02 — Request

HTTP request — four parts

Every HTTP request has the same four parts. Once you can name them, you can read any request the browser, curl, or DevTools shows you.

Request
  1. URL — where the resource lives
  2. Method — what operation to perform
  3. Headers — metadata about the request
  4. Body — the payload (when applicable)
A concrete example
POST /login HTTP/1.1
Host: 127.0.0.1:3000
Content-Type: application/x-www-form-urlencoded
Cookie: session=abc123…
Content-Length: 38

username=alice&password=hunter2

1. URL — the resource location

The URL identifies which resource the request is about. In express-auth:

URLIdentifies
/the protected home page (read your own session)
/loginthe login form (and the action that creates a session)
/signupthe signup form (and the action that creates a user)
/api/passwordthe current user's password
/api/accountthe current user's account

2. Method — the operation

The method tells the server what to do with the resource. Four methods cover almost every CRUD app:

MethodMeaningIn express-auth
GETRead / retrieve a resource. Should be safe (no side effects).Fetch a page like /login or the home view
POSTCreate a new resource (or perform a non-idempotent action).POST /signup creates a user; POST /login creates a session
PUTUpdate / replace an existing resource.PUT /api/password updates the current user's password
DELETERemove an existing resource.DELETE /api/account deactivates the current user

3. Headers — metadata about the request

Headers carry extra information about the request that isn't part of the URL or body. A few you'll see constantly:

HeaderWhat it carries
HostWhich virtual host the request is for (required in HTTP/1.1)
Content-TypeFormat of the body: application/x-www-form-urlencoded for forms, application/json for AJAX
Content-LengthSize of the body in bytes
CookieStored cookies the browser sends back — this is how express-auth recognizes a logged-in user (Cookie: session=…)
AuthorizationCredentials for API-style auth (e.g. Bearer <token>) — not used in this app, but ubiquitous in APIs
AcceptWhat content types the client wants back (text/html, application/json, …)
Two important headers in this app:
  • Cookie (request) — express-auth reads the session=… cookie on every request to look up the logged-in user.
  • Content-Type (request) — forms send application/x-www-form-urlencoded; the AJAX pages send application/json. Express picks a different body parser based on this header.

4. Body — the payload

The body carries the data the server needs to act on. GET requests almost never have one; POST/PUT/DELETE often do. The body's format is whatever the Content-Type header says.

form body — url-encodedPOST /login
Content-Type: application/x-www-form-urlencoded

username=alice%40example.com&password=hunter2
ajax body — jsonPUT /api/password
Content-Type: application/json

{
  "currentPassword": "hunter2",
  "newPassword":     "correct horse battery staple"
}
§ 03 — Response

HTTP response — three parts

The reply has a symmetric shape — a status, headers, and a body — but no URL or method (the request already told the server what to do).

Response
  1. Status — did it work? (three-digit code + reason)
  2. Headers — metadata about the reply
  3. Body — the payload (HTML page or JSON data)
A concrete example
HTTP/1.1 302 Found
Location: /
Set-Cookie: session=abc123…; HttpOnly; Path=/
Content-Length: 0

(empty body — the browser follows Location)

1. Headers — metadata about the reply

Headers tell the browser how to interpret what comes next. The most useful ones for this app:

HeaderWhat it carries
Content-TypeFormat of the body: text/html, application/json, text/plain, …
Content-LengthSize of the body in bytes
Set-CookieAsks the browser to store a cookie. express-auth uses it to start and clear sessions: Set-Cookie: session=…; HttpOnly; Path=/
LocationUsed with a 3xx status — tells the browser where to go next
AllowUsed with 405 Method Not Allowed — lists the methods this URL accepts
How sessions stay alive between requests: the server sends Set-Cookie: session=… once (after login). The browser stores it. On every later request, the browser includes Cookie: session=… automatically. The server reads the cookie, looks up the session, and recognizes the user. This is the whole session loop.

2. Body — the payload

The body is whatever the page or API needs to deliver. Two common shapes in this app:

Page content (view)

  • Content-Type: text/html
  • The full HTML document the browser renders
  • Used by GET /, GET /login, GET /signup

Data only (JSON)

  • Content-Type: application/json
  • A small JSON object the page's JavaScript reads
  • Used by PUT /api/password, DELETE /api/account

The codes you'll see in this app

CodeMeaningWhere it appears
200 OKRequest succeeded; body holds the resultMost GETs; successful PUT /api/password
201 CreatedA new resource was createdCommon shape for "create" endpoints (this app uses 302 redirects instead, but 201 is the textbook answer)
302 FoundTemporary redirect — follow LocationAfter login, signup, logout — the server steers the browser to the next page
304 Not ModifiedCached copy is still freshStatic assets like /forms.css on a reload
400 Bad RequestClient sent invalid dataPUT /api/password with a short or missing password
401 UnauthorizedNo (or invalid) credentialsPUT /api/password or DELETE /api/account without a session cookie
403 ForbiddenAuthenticated but not allowedNot used here, but common in apps with roles
404 Not FoundNo resource at this URLAny unknown GET path — the catch-all in express-server.js
500 Internal Server ErrorThe server crashed handling the requestBugs in your handler — what every developer wants to avoid in production
Rule of thumb: if the status is 4xx, fix the request. If it's 5xx, fix the server. 3xx means "I'm not the right place — try here." 2xx means everything worked.

Mapping methods to resources

The capstone app uses every method against one resource — the user. Read the table below as the contract you'll exercise in the labs that follow.

§ 05 — Two ways

Two ways a browser sends HTTP requests

From a browser, there are exactly two practical ways to send an HTTP request. They look the same to the server — same TCP socket, same HTTP envelope — but they give the developer very different control over the user's page flow.

1. HTML form (no script needed)

  • The browser submits when the user clicks the button.
  • Body is automatically application/x-www-form-urlencoded.
  • The browser follows the server's reply — if the response is HTML, it renders; if it's a 302, it navigates.
  • No JavaScript required. Works with JS disabled.
  • Page flow is controlled by the server.
  • Used here for: POST /signup, POST /login.

2. AJAX (fetch from script)

  • JavaScript builds and sends the request itself.
  • You pick the body format (application/json is the default).
  • The reply lands in a JS object — the page decides what to render or where to navigate.
  • Required for whole methods like PUT and DELETE (HTML forms only do GET/POST).
  • Page flow is controlled by the page (client).
  • Used here for: PUT /api/password, DELETE /api/account.
Why forms can't do PUT/DELETE on the wire: the HTML spec's <form method> attribute only accepts get, post, and dialog. Writing method="PUT" is an invalid value and the browser silently falls back to GET. To put a real PUT or DELETE on the wire from a browser, you need script — which is why express-auth uses AJAX for those endpoints.
The _method override trick: some frameworks (Rails, Laravel, Express with method-override) let a form post a hidden field like <input type="hidden" name="_method" value="PUT"> and rewrite req.method server-side. On the wire it's still a POST — the framework just pretends it was a PUT inside the handler. Useful for progressive enhancement, but it isn't a real PUT request, and it can't reach a strict app.put(...) route on a server that doesn't run the override middleware.
§ 06 — Hands-On · Form

POST + form — signup

Goal: create a new user with a plain HTML form. The browser submits the form, the server creates the user resource, and the server's response steers the browser to the next page. No JavaScript involved.
Lab 1A — Submit the signup form
1
Open http://127.0.0.1:3000/signup. The page is just public/signup.html — three text inputs inside a <form method="POST" action="/signup">. The browser will do all the work.
signup.html (excerpt)html form
<form method="POST" action="/signup">
  <input name="displayName" required>
  <input name="username"    type="email" required>
  <input name="password"    type="password" required>
  <button type="submit">Sign up</button>
</form>
2
Fill in the fields and click Sign up. Open DevTools → Network before you click so you can see the request the browser sends. You'll see exactly one POST.

§ 07 — Hands-On · Form

POST + form — login (creates a session)

Goal: create a session resource. Same shape as signup — a plain HTML form posts username and password — but this time the server's reply includes a Set-Cookie header that the browser stores for every future request.
Lab 2A — Log in and watch the cookie appear
1
Open DevTools → Application → Cookies → http://127.0.0.1:3000. It's empty. Now open http://127.0.0.1:3000/login, fill in the user you just created in Lab 1A, and submit.
browser POSTPOST /login
POST /login HTTP/1.1
Host: 127.0.0.1:3000
Content-Type: application/x-www-form-urlencoded

username=alice%40example.com&password=hunter2
2
The server validates the credentials, creates a session id, and returns a 302 redirect to / — but it also attaches a Set-Cookie header. The browser stores the cookie before following the redirect.
server response302 + Set-Cookie
HTTP/1.1 302 Found
Location: /
Set-Cookie: session=8f3c…ab12; HttpOnly; Path=/
Content-Length: 0
3
The browser follows the redirect by sending GET / — and this time it includes Cookie: session=… in the request. The server reads the cookie, looks up the session, and renders the protected home page.
next request from the browserGET / with cookie
GET / HTTP/1.1
Host: 127.0.0.1:3000
Cookie: session=8f3c…ab12
This is the session loop:
  1. Set-Cookie goes server → browser once.
  2. Cookie goes browser → server on every subsequent request.
  3. The server uses the cookie to find the user. No login form needed again.
Lab 2B — Log in with curl and reuse the cookie
1
Use -c cookies.txt to capture the Set-Cookie jar, then -b cookies.txt to send it back. This is exactly what the browser does silently.
curl — capture and reuse cookies-c / -b
# Log in, save the Set-Cookie into cookies.txt
curl -i -c cookies.txt -X POST http://127.0.0.1:3000/login \
  -H "Content-Type: application/x-www-form-urlencoded" \
  --data-urlencode "username=alice@example.com" --data-urlencode "password=hunter2"

# Now use the cookie on the protected page
curl -i -b cookies.txt http://127.0.0.1:3000/
# HTTP/1.1 200 OK
# Content-Type: text/html
# <... home page HTML ...>
Try this: request GET / without -b cookies.txt. You'll get a 302 → /login instead — exactly the same path the browser takes the first time you visit, before any session exists.
§ 08 — Hands-On · AJAX

PUT + AJAX — change password

Goal: update the current user's password using a method (PUT) that HTML forms can't send. The page builds the request itself, sends JSON, reads JSON back, and decides where to navigate. Page flow stays in the page's hands.
Lab 3A — Send a PUT from the page
1
With your session cookie still in place from Lab 2, open http://127.0.0.1:3000/change-password. The page renders two inputs and a button. The button is not a form submit — it runs a small fetch call.
change-password.html (excerpt)fetch PUT
const response = await fetch("/api/password", {
  method: "PUT",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({
    currentPassword: currentPassword,
    newPassword:     newPassword
  })
});

const data = await response.json();
if (!response.ok) showMessage(data.error, "error");
else            window.location.href = "/";
2
Enter your current password and a new one (8+ characters), and click Send PUT request. Watch DevTools → Network. You'll see exactly one request, with method PUT and a JSON body.
browser requestPUT /api/password

Host: 127.0.0.1:3000
Content-Type: application/json
Cookie: session=8f3c…ab12

{"currentPassword":"hunter2","newPassword":"correct-horse-staple"}

The server replies with JSON. On success, 200 OK and a small {message}. On failure, 400 or 401 with an {error} field.

Client-driven page flow: notice the JS reads data.message and chooses to navigate to / itself with window.location.href = "/". The server didn't tell it to — the page made the decision. That's the difference from the form labs.

§ 09 — Hands-On · AJAX

DELETE + AJAX — deactivate account

Goal: remove the current user resource. DELETE is the cleanest expression of "destroy this thing" — and again, HTML forms can't send it. AJAX is the only browser-native way to issue a DELETE.
Lab 4A — Send the DELETE
1
Make sure you're logged in (re-run Lab 2A if you cleared the cookie). Open http://127.0.0.1:3000/deactivate-account. The page is a single button. Read the page source.
deactivate-account.html (excerpt)fetch DELETE
const confirmed = window.confirm("Delete this account and log out?");
if (!confirmed) return;

const response = await fetch("/api/account", { method: "DELETE" });
const data     = await response.json();

window.location.href = data.redirect || "/signup";
2
Click Send DELETE request. Confirm the prompt. Watch the Network tab — a single DELETE request with no body.
browser requestDELETE /api/account
DELETE /api/account HTTP/1.1
Host: 127.0.0.1:3000
Cookie: session=8f3c…ab12
3
The server deletes the user, clears the session cookie with Set-Cookie: session=; Max-Age=0, and returns JSON with a redirect field. The page reads that field and navigates to /signup.
server reply200 OK · clear cookie
HTTP/1.1 200 OK
Set-Cookie: session=; HttpOnly; Path=/; Max-Age=0
Content-Type: application/json

Two cookie operations, same header: Set-Cookie is used to start a session (login) and to end one (logout, deactivate). The "end" version sends an empty value and Max-Age=0, which tells the browser to forget the cookie immediately.

# {"message":"Account deleted.","redirect":"/signup"}
§ 10 — Beyond

Cookies & sessions in one picture

HTTP itself is stateless — every request stands alone. Sessions are the trick that makes a stateless protocol feel like a continuous conversation. The whole mechanism is just two headers:

DirectionHeaderPurpose
server → browserSet-Cookie: session=…Ask the browser to store this cookie
browser → serverCookie: session=…Send all stored cookies automatically on every request to the same origin

In express-auth the value is just a random hex string (a session id). The server keeps a Map<sessionId → user> in memory in store.js. Combine the two and you get:

full session lifecyclelogin → use → logout
# 1. login — server starts a session
POST /login      → 302 + Set-Cookie: session=abc

# 2. every later request — browser sends the cookie automatically
GET /            ← Cookie: session=abc  → 200 OK · home page
PUT /api/password ← Cookie: session=abc  → 200 OK

# 3. logout / deactivate — server clears the cookie
GET /logout     → 302 + Set-Cookie: session=; Max-Age=0
HttpOnly: express-auth sets the cookie with HttpOnly. That tells the browser to hide the cookie from document.cookie — JavaScript on the page can't read it. The browser still sends it on every request, but XSS scripts can't steal the session id. Always set HttpOnly on session cookies.
§ 11 — Beyond

Inspecting HTTP traffic

Everything in this lab is text on a TCP socket. You have three ways to see it — pick whichever fits the moment.

1. Browser DevTools — Network tab

Open DevTools, switch to Network, click any request. The right panel shows Headers (request + response), Payload (body), Response (raw body), and Cookies. This is the fastest way to see what your page is actually sending.

2. curl -i from a terminal

curl -i prints the full response (status + headers + body). Combine with -c / -b for cookies and -X / -H / -d for request shaping. Every lab above includes a curl equivalent for this reason.

3. Raw socket — like IPC Hands-On Lab 3B

Because HTTP is just bytes, you can speak it with socketer.js or ncat. Connect to port 3000 and type the request yourself:

raw HTTP over socketertype the request
node ../ipc/socketer.js 127.0.0.1 3000
# then type, exactly:
GET /login HTTP/1.1
Host: localhost
                  (← blank line — press Enter twice)
# Server replies with the full HTTP response stream.
This is the moment the stack collapses: the same socket you used in IPC Hands-On is now carrying HTTP. The same HTTP is what your browser sends. The same browser-built request is what fetch assembles. One protocol, every layer.
§ 12 — Wrap-up

Wrap-up — the whole picture

You now have the full vocabulary for building HTTP applications:

  • A request = URL + method + headers + body.
  • A response = status + headers + body.
  • Five status families (1xx info, 2xx ok, 3xx redirect, 4xx client error, 5xx server error).
  • Four methods map to CRUD: GET read, POST create, PUT update, DELETE remove.
  • Two ways the browser sends requests: HTML form (server controls flow) or AJAX (page controls flow).
  • Two cookie headers — Set-Cookie and Cookie — turn stateless HTTP into a session.
From bytes to applications
pipe moves stdout → stdin between processes  ·  socket moves bytes between processes over TCP
HTTP structures those bytes into request & reply  ·  Form / AJAX picks who controls page flow
Express + Set-Cookie turn the whole stack into a real product

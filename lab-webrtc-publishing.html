The Goal
browser captures → publishes over WebRTC → MediaMTX serves it to everyone
No app install, no plugin — a web page is the camera. This is how you'd add "stream from your phone" to the VMS. WHIP = the standard HTTP way to start a WebRTC publish; MediaMTX speaks it natively.
01 — The Media Device API
one call gets a live MediaStream; a stream is a bag of tracks
camera + mic
const stream = await navigator.mediaDevices
  .getUserMedia({ video: true, audio: true });

video.srcObject = stream;   // preview
screen (+ system audio)
const stream = await navigator.mediaDevices
  .getDisplayMedia({ video: true, audio: true });
a stream is made of tracks
stream.getVideoTracks()  // [VideoTrack]
stream.getAudioTracks()  // [AudioTrack]

const t = stream.getVideoTracks()[0];
t.label      // "FaceTime HD Camera"
t.enabled = false   // mute / pause
t.stop()      // release the device
Secure context required: these APIs only work on https:// or localhost. On a phone hitting http://192.168.x.x they're blocked — see the lab's HTTPS step.
Mobile reality: getUserMedia (camera) works great on phones. getDisplayMedia (screen share) is not supported on most mobile browsers — that button is desktop-only.
02 — How WebRTC Connects
signaling is out-of-band; media flows peer-to-peer
The two sides first describe themselves to each other (SDP: codecs, IPs, keys) over an HTTP channel — that's WHIP. Once they agree, encrypted media flows on its own UDP path. Offer goes out, answer comes back, done.
03 — ICE · Finding a Path Through NAT
STUN discovers your public address · TURN relays when direct fails
ICE gathers every possible route (local IP, STUN-discovered public IP, TURN relay), tries them, and keeps the best. On a LAN it connects directly — stun:stun.l.google.com:19302 is enough for the lab. You only need TURN to cross strict corporate firewalls or the open internet.
04 — Inside a Connection: Streams, Tracks & Data
media rides SRTP, arbitrary data rides a DataChannel — same secure transport
For this lab we only push tracks (camera video + mic audio). The DataChannel sibling is how WebRTC also moves files, chat, or game state over the very same connection — good to know, not needed here.
05 — Codec Support by Browser
WebRTC negotiates a codec both sides share — but the default pick matters

Chrome tends to offer VP8/VP9 (webm) first. That plays fine over WebRTC and HLS — but it breaks the moment you want RTMP, which is H.264-only. The next slide fixes this.
05 — Force H.264 for Compatibility
reorder the codec list before the offer so every player works
// add tracks as send-only transceivers
stream.getTracks().forEach(t =>
  pc.addTransceiver(t, {
    direction: 'sendonly', streams:[stream]
  }));

// prefer H.264 on the video transceiver
const caps = RTCRtpSender
  .getCapabilities('video').codecs;
const h264 = caps.filter(c =>
  c.mimeType === 'video/H264');

pc.getTransceivers().forEach(tx => {
  if (tx.sender.track?.kind === 'video')
    tx.setCodecPreferences(
      [...h264, ...caps.filter(c=>
        c.mimeType!=='video/H264')]);
});
Why: publish H.264 + Opus and your single stream is readable over WebRTC, HLS, and RTSP without any server-side transcoding.
Without this: Chrome picks VP8 → RTMP playback fails, and HLS over older players needs a transcode. One line of codec ordering saves a lot of pain.
setCodecPreferences is supported in current Chrome, Edge, Firefox, and Safari. If H.264 isn't in the caps list, the browser falls back gracefully to the next codec.
06 — WHIP · Publish in 4 Steps
getUserMedia → offer → POST to MediaMTX → apply answer
// 1 · capture + peer connection
const stream = await navigator.mediaDevices.getUserMedia({ video:true, audio:true });
const pc = new RTCPeerConnection({ iceServers:[{ urls:'stun:stun.l.google.com:19302' }] });
stream.getTracks().forEach(t => pc.addTransceiver(t, { direction:'sendonly', streams:[stream] }));

// 2 · create the offer (SDP)
await pc.setLocalDescription(await pc.createOffer());

// 3 · POST the offer to MediaMTX's WHIP endpoint
const res = await fetch(`http://localhost:8889/${path}/whip`, {
  method:'POST', headers:{ 'Content-Type':'application/sdp' }, body:pc.localDescription.sdp });

// 4 · apply MediaMTX's answer → media starts flowing
await pc.setRemoteDescription({ type:'answer', sdp: await res.text() });
That's the whole publish handshake. MediaMTX now has your stream on path ${path} and will serve it on every protocol it supports. To stop cleanly, pc.close() and DELETE the resource URL from the response's Location header.
06 — WHEP · Play in the Browser
the mirror image of WHIP — recvonly instead of sendonly
const pc = new RTCPeerConnection();

// we only receive
pc.addTransceiver('video', {direction:'recvonly'});
pc.addTransceiver('audio', {direction:'recvonly'});

pc.ontrack = (e) => {
  video.srcObject = e.streams[0];
};

await pc.setLocalDescription(
  await pc.createOffer());

const res = await fetch(
  `http://localhost:8889/${path}/whep`, {
  method:'POST',
  headers:{'Content-Type':'application/sdp'},
  body: pc.localDescription.sdp });

await pc.setRemoteDescription({
  type:'answer', sdp: await res.text() });
Easiest path of all: MediaMTX ships a built-in player page. Just open http://localhost:8889/<path> in any browser — no code needed to verify a publish.
WHEP is identical in shape to WHIP: build an offer, POST it to the /whep endpoint, apply the answer. The only differences are recvonly transceivers and reading frames in ontrack.
07 — Build the Publisher UI
two cards: camera + screen, each with preview, path field, start/stop
Provided: webrtc-publisher.html — a complete, responsive, single-file app. It extends the starter with H.264 forcing, a secure-context check, mobile layout, and a clean stop/teardown.
Toggle logic per card: not active → capture, build offer, WHIP POST, show preview, flip button to Stop. Active → close PC, stop tracks, clear preview.
On mobile the two cards stack, and the Screen card auto-disables (no getDisplayMedia).
08 — Play the Published Stream Anywhere
one WebRTC publish, many ways out — codec decides what's possible
ProtocolHow to playCodecsLatency
WebRTC (WHEP)browser → localhost:8889/<path>H264 · VP8/9 · AV1 · Opussub-second
HLSbrowser → localhost:8888/<path>H264 · H265 · AV1 (+Opus in fmp4)~2–6 s
RTSPffplay / VLC → :8554/<path>almost alllow
RTMPffplay / OBS → :1935/<path>H264 + AAC only~2 s
The codec rule, made concrete: publish VP8 (Chrome default) → WebRTC ✓ HLS ✓ but RTMP ✗. Publish H.264 (forced, slide 8) → all four work. That single choice is why we reorder codecs in the publisher.
